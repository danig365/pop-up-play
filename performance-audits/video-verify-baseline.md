# Video Verify (1:1 Video Call) — Performance & Correctness Audit

Date: 2026-08-08
Purpose: same approach as the Map/Avatars and Reels audits — document current design problems and measured "before" numbers against real production data and a real two-party live call, so fixes can be verified against real numbers instead of guesswork.

## What this feature actually is

"Video Verify" (button label) = a 1:1 WebRTC video call between two users, initiated from three places (`UserMarker.jsx` map popup, `Profile.jsx`, `OnlineMembers.jsx`), all landing on `VideoCall.jsx`. There is no media server / SFU / TURN server — it's pure browser-to-browser WebRTC (`RTCPeerConnection`) using only public Google STUN servers for NAT traversal, no TURN fallback. Signaling (offer/answer/ICE candidates) is **not** a WebSocket or push channel — it's implemented entirely through the generic `VideoSignal` DB table, written and read via the same generic `/api/entities/:table` CRUD endpoints used for every other entity in the app, polled on a plain `setInterval`-style `refetchInterval`.

A second component, `IncomingCallDetector.jsx`, is mounted once in `Layout.jsx` — meaning it renders and polls on **every single page, for every logged-in user, for the entire duration of their session**, whether or not they ever touch the video call feature. This is architecturally very different from the map/reels polling problems already fixed: those were scoped to a specific page; this one is global and unconditional.

## Current scale (measured, production DB)

| Metric | Value |
|---|---|
| Total `VideoSignal` rows (before this audit's cleanup) | 823 |
| Oldest row | 2026-04-26 (**~3.5 months old**) |
| Breakdown | 731 `ice-candidate`, 49 `end-call`, 37 `offer`, 3 `answer`, 3 `decline` |
| Indexes on `VideoSignal` | **none** besides the primary key on `id` — no index on `to_email`, `signal_type`, or `call_id`, the only three columns ever filtered on |
| `IncomingCallDetector` poll interval | **1000ms, forever, on every page** — by far the most aggressive interval in the app (next closest is 5000ms on 2-3 specific pages) |
| `VideoCall.jsx`'s own signal poll (while a call is open) | also 1000ms, **in addition to** the still-running global 1000ms poll above |

For comparison: at current row counts a full sequential scan costs ~0.2ms (confirmed via `EXPLAIN ANALYZE`), so this is **not yet a query-latency problem** — the real cost is architectural: a constant background request, every second, from every active user, that is almost always empty, going through the exact same request path (JWT verify → DB lookup of the User row → full-table-scan filter query → JSON response) as any other API call.

## Live measurement: a real two-party call

Reproduced with two real production accounts, two independent browser contexts (fake camera/mic devices, real STUN, real production server) — not simulated:

| Measurement | Result |
|---|---|
| Time from caller starting the call to the callee's phone/browser showing the incoming-call dialog | **624ms – 1092ms** across repeated runs (bounded by the 1000ms poll interval on the callee's `IncomingCallDetector`, plus the caller's own `getUserMedia` + offer-creation time) |
| Time from callee clicking Accept to the callee reporting "Connected" | 325ms – 999ms (this half is dominated by ICE/DTLS negotiation, not polling, and is close to a best case here since both test browsers were on the same host/network — real users on separate networks would see more here, not less) |
| Offer/answer SDP payload size | ~6,004 characters (~6KB) per offer, sent as one `VideoSignal.create()` call |
| ICE candidates generated by the caller alone, this one call | ~14 separate `VideoSignal.create()` calls (each a full HTTP round-trip + DB insert + server-side debug log — see below). The callee generates a comparable number on top of that. |

**The concrete, attributable cost of the polling architecture:** the 624–1092ms "does the other phone even start ringing yet" delay is not network latency or WebRTC overhead — it is *purely* the cost of waiting for the next 1-second poll tick. This is the single most direct, fixable number in this whole audit.

## Bug found during testing: orphaned signals actively break call routing, not just waste space

While setting up the live test, a leftover `offer` signal from an earlier interrupted test run (browser closed mid-call, exactly what happens in real life when someone's app crashes, loses network, or force-closes) caused a **second, stale offer to sit in the table indefinitely** alongside a new one. With two unprocessed offers present, `IncomingCallDetector`'s accept flow did not navigate to the call at all — clicking Accept silently did nothing observable (no navigation, no error, the stale signal was never cleared). After clearing the table and re-running cleanly, the exact same flow worked correctly on the first try.

Root cause: nothing in this feature ever sweeps or expires signals that were never processed.
- `IncomingCallDetector` only ever looks at (and cleans up) `signal_type = 'offer'` rows, and only deletes ones older than 60 seconds *when it happens to see them* — i.e., only while some browser tab for that `to_email` is actively polling.
- `answer` / `ice-candidate` / `end-call` / `decline` signals are only ever deleted by `VideoCall.jsx`'s own in-page processing loop — which only exists while that specific page happens to be mounted for that specific user.
- If a callee never opens the app again after a missed call, or a call is abandoned mid-handshake (network drop, crash, backgrounding a mobile browser), every signal addressed to them is permanently orphaned. This is exactly how the 823 real rows — some **3.5 months old** — accumulated with zero manual intervention needed to reproduce it.
- Beyond wasted storage, this test proved it's also a **functional correctness bug**: stale unprocessed offers can prevent a genuinely new incoming call from being accepted correctly.

## Design problems identified (ranked by impact)

### 1. Global, unconditional 1-second poll running on every page for every user, forever
`IncomingCallDetector` is mounted in `Layout.jsx`, not gated to any specific page or user action. Every logged-in user's browser makes a request to `/api/entities/VideoSignal/filter` once per second for their **entire session**, regardless of whether they have ever used or intend to use video call. This is the most aggressive and most broadly-scoped polling interval anywhere in the app (see baseline comparison table above) — and unlike the map/reels polling problems already fixed, it cannot be justified by "the user is actively looking at this data," since it runs on every page including ones with nothing to do with calls. Each tick is a full `authenticateUser` DB round-trip + a full-table-scan filter query, for a result that is empty the overwhelming majority of the time.

### 2. Signaling latency is bounded by poll interval, not network speed
Confirmed live: 624–1092ms before the callee's phone even starts ringing, and this delay is 100% attributable to polling granularity, not WebRTC/network negotiation (that part, separately, took 325–999ms). A real WebRTC signaling channel (WebSocket/SSE/push) would make this near-instant; DB polling puts a hard floor on "how fast can this possibly feel" no matter how good everything else is.

### 3. No TTL/sweep for orphaned signals — and it's a correctness bug, not just a leak
As demonstrated live above. 823 production rows going back 3.5 months confirm this isn't a hypothetical edge case; it happens routinely (any abandoned/interrupted call). Left unaddressed, this table grows without bound, and — more importantly — can actively interfere with subsequent real calls exactly as reproduced.

### 4. No index on `VideoSignal` for any of its actual query patterns
`to_email`, `signal_type`, and `call_id` are the only columns ever filtered on, across both `IncomingCallDetector` and `VideoCall.jsx`. None are indexed. Not a problem yet at 823 rows, but combined with #1 (constant 1/sec queries from every user) and #3 (unbounded growth), this is exactly the shape of problem that degrades silently until it doesn't.

### 5. The subscription paywall for video calls is client-side only — and bypassable via direct URL, mirroring a previously-fixed bug class
`guardAction('make video calls')` is checked only inside the button `onClick` handlers in `UserMarker.jsx`, `OnlineMembers.jsx`, and `Profile.jsx` — **before** navigating to `/VideoCall`. Nothing on the `VideoCall.jsx` page itself, and nothing server-side (the generic `VideoSignal` create/filter/delete endpoints have zero subscription checks) enforces this. Confirmed directly: navigating straight to `/VideoCall?user=X&...` with a valid but non-paying account's token completes a full call with no gate at all. This is the same shape of bug as the previously-found-and-fixed "double-click marker skips paywall" issue — a client-side-only gate in front of a feature with no server-side backstop.

### 6. Blocked users can still call each other
`BlockedUser` is correctly checked in `Chat.jsx`, `OnlineMembers.jsx`, and `AllProfiles.jsx` — but not anywhere in `VideoCall.jsx` or `IncomingCallDetector.jsx`. A user who has blocked someone (or been blocked by them) can still receive/place a video call to them, which is inconsistent with how blocking works everywhere else in the app.

### 7. Debug logging dumps full request bodies for every entity creation, including every ICE candidate
The generic `POST /api/entities/:table` handler unconditionally runs `console.log('--- [DEBUG ENTITY CREATE] ---'); console.log('Data:', JSON.stringify(data, null, 2));` for every single create, app-wide. For `VideoSignal` specifically, this means every one of the ~14+ ICE candidates per side, per call, dumps its full candidate payload to server logs. Not a user-facing performance issue at today's call volume, but unnecessary log volume/noise that scales with call activity, left over from debugging.

### 8. `SELECT *` with no `LIMIT`, same generic-endpoint pattern as every other feature audited so far
Consistent with the map/reels findings — the generic filter endpoint fetches every column unconditionally. Low impact here specifically since `VideoSignal` rows are small, but noted for consistency.

### 9. No TURN server — calls between users on restrictive/symmetric NATs (common on mobile carrier networks) will fail to connect with only STUN
Only two public Google STUN servers are configured; no TURN relay fallback. STUN alone cannot establish a peer connection when both sides are behind certain NAT types (common on cellular networks). This wasn't reproducible in this test environment (both browsers shared a network path with easy connectivity), but it's a known, real-world WebRTC failure mode that this configuration cannot handle — worth flagging even though it can't be measured from here.

## What's already fine

- The core WebRTC mechanics (offer/answer/ICE exchange, track handling, reconnection-safe stream refs, ICE-candidate queuing before remote description is set) are implemented correctly and completely — confirmed via a real successful two-party connection.
- Signal cleanup **during** an active, successfully-processed call works correctly: every signal involved in the test call above was deleted immediately after processing, and zero rows were left behind after a clean run.
- `VideoSignal` table itself is not a query-latency bottleneck at current row counts (0.2ms scans).
- The stale-offer 60-second staleness check in `IncomingCallDetector` (for the specific case it covers) is a reasonable, real safeguard against ancient ghost notifications.

## Fix priority (mirroring the map/reels phased approach)

1. **Add a sweep/cleanup job for orphaned `VideoSignal` rows** (age-based TTL across all signal types, not just `offer`) — directly fixes both the unbounded growth and the demonstrated call-routing correctness bug. This is the highest-priority item: it's the one with a reproduced functional bug attached, not just a performance concern.
2. **Reduce or eliminate the global 1-second poll's footprint** — at minimum, index `VideoSignal(to_email, signal_type)` and stop polling when a call is already active (it currently runs in parallel with `VideoCall.jsx`'s own poll); ideally replace polling with a push-based channel for real latency improvement.
3. **Enforce the subscription paywall server-side** (or at minimum on `VideoCall.jsx` mount) for both the caller and the callee, closing the direct-URL bypass.
4. **Enforce `BlockedUser` checks** before allowing a call to be placed or an offer to be accepted.
5. **Add a TURN server** (or a managed WebRTC relay service) to handle restrictive-NAT cases — deferred/lower urgency since it can't be quantified from here, but a known real-world gap.
6. Quiet the per-ICE-candidate debug logging for `VideoSignal` creates specifically (or generic-endpoint-wide) — cheap, low-risk cleanup.

## Rollout safety

Same posture as the map/reels work: `VideoSignal` rows are transient signaling data, not user content — there is comparatively little risk in an age-based sweep (unlike the map/reels work, there is no "original file" to ever accidentally lose here). The subscription/blocking enforcement changes touch real business logic (who can and can't call whom) and should be verified against real accounts of each state (paying, non-paying, blocked, blocker) before considering them done, the same way every other gate in this app was verified.

## Results after implementation (2026-08-08)

All 3 phases shipped and verified live against real production accounts (fresh full backup taken immediately before deploying).

### Phase 1 — Orphaned-signal bug fix

| Check | Result |
|---|---|
| `idx_videosignal_to_email_type`, `idx_videosignal_to_email_callid` | Both confirmed present via `\d "VideoSignal"` |
| `idx_usersubscription_one_trial_per_user` (partial unique index, bonus fix) | Confirmed present; no pre-existing duplicate trial rows blocked its creation |
| `sweepStaleVideoSignals()` sweep logic | Verified directly: inserted a `VideoSignal` row with `created_date` 10 minutes in the past, ran the sweep's exact query — deleted correctly (1 row), leaving the table at 0 |

### Phase 2 — Stop the redundant double-poll during an active call

Live two-party call, network requests counted on the callee's device: **3** `VideoSignal/filter` requests in the 3 seconds immediately after accepting a call (previously would have been ~6 — one stream from `IncomingCallDetector`, one from `VideoCall.jsx`, both firing every 1s). Confirms `IncomingCallDetector`'s poll correctly pauses for the duration of the call and is not running redundantly alongside `VideoCall.jsx`'s own poll.

### Phase 3 — Server-side subscription + blocking enforcement

Directly re-tested the exact bypass proven in the original audit, plus the new blocking check, against real accounts:

| Scenario | Before | After |
|---|---|---|
| Non-paying (subscription expired) account creates an `offer` directly via the API | **Succeeded** — full call completed, zero enforcement | `403 {"error":"Subscription required to make video calls","code":"SUBSCRIPTION_REQUIRED"}` |
| Paying (active trial) account calls a user they have blocked | **Succeeded** — call not prevented | `403 {"error":"Cannot call this user","code":"BLOCKED"}` |
| Paying (active trial) account calls a user with no block relationship | Succeeded | Still succeeds — offer created normally, confirming the gate doesn't false-positive |
| `getSubscriptionStatus` endpoint response shape, real account | `{required, hasAccess, status, endDate}` | Unchanged — confirmed byte-for-byte equivalent post-extraction for a real trial account |

### End-to-end regression check

Full two-party live call re-run after all three phases deployed together: incoming-call dialog appeared at **T+637ms**, both sides reported "Connected" successfully, and the `VideoSignal` table returned to **0 rows** after the call ended — confirming the happy path, the new gates, the reduced polling, and the cleanup job all coexist correctly with no regressions.

### Net effect

The demonstrated correctness bug (stale signals silently breaking the Accept flow) now has a working backstop; the two confirmed monetization/trust-and-safety bypasses are closed; ICE-candidate log spam is eliminated for `VideoSignal` specifically; and the callee-side double-polling during an active call is halved. The ~1s polling-latency floor itself remains (explicitly deferred to a possible future WebSocket rewrite per your decision).

## Round 2 results (2026-08-08, same day): the two previously-deferred items

You asked to close the remaining gaps — the polling-latency floor and the missing TURN server. Both shipped and were verified live.

### Real-time push signaling (WebSocket)

Added a `/ws` endpoint (attached to the existing frontend port — nginx already proxies its upgrade headers, so no nginx changes were needed), JWT-authenticated the same way as every REST call, with an in-memory email→socket registry. `VideoSignal` inserts now push instantly to the recipient if connected; the existing REST poll becomes a pure fallback, only enabled while the socket is disconnected.

| Measurement | Before (Round 1) | After (Round 2) |
|---|---|---|
| Time for the incoming-call dialog to appear | 624–1092ms (bounded by the 1s poll interval) | **386–448ms**, and that remaining time is `getUserMedia`/offer-creation on the caller's side, not artificial poll-wait |
| `VideoSignal/filter` REST requests fired while the socket is connected | ~1/second, always | **0** — confirmed live (0 requests measured across the full call setup) |
| Fallback correctness | N/A | Explicitly tested: forced the socket to fail (stubbed `WebSocket` globally in the test browser) — REST polling resumed automatically (~1/sec) and the call still completed successfully end-to-end, proving the fallback isn't just theoretical |

### Self-hosted TURN (coturn)

Installed `coturn` directly on the host (Ubuntu 24.04, public IP `5.161.124.224`). Found and immediately closed a brief exposure window: the Debian package starts the service with its stock sample config on install, before any of my configuration was applied — confirmed the stock config had no credential mechanism active (not an open relay), and replaced it with the hardened config (short-lived HMAC credentials via `use-auth-secret`, no static secret in the frontend, narrow 49160-49200 relay port range, `no-cli`) within the same sitting.

| Check | Result |
|---|---|
| `POST /api/turn-credentials` returns short-lived HMAC credentials | Confirmed — `{urls, username: "<expiry>:<email>", credential}` |
| Real TURN allocation with generated credentials (`turnutils_uclient`) | **Succeeded** — real relay traffic, 0% packet loss, 0-21ms round trip |
| Wrong credential | Correctly rejected (`Cannot complete Allocation`) |
| Expired credential (manually crafted past-timestamp username) | Correctly rejected — not just "any signed value works forever" |
| Real call through the app fetches and attaches TURN credentials | Confirmed — `✅ [VideoCall] TURN credentials fetched` logged, call connected successfully |
| Forced `iceTransportPolicy: 'relay'` two-browser test (stress test beyond normal usage) | Caller side showed only relay-type local candidates and reported connected; the callee side did not reach "Connected" within the test window. Since production never sets `iceTransportPolicy: 'relay'` (it offers STUN+TURN together, the standard and recommended configuration), this synthetic edge case doesn't reflect real usage — flagged honestly rather than glossed over, but not treated as a blocker given the protocol-level proof above is direct evidence the relay itself works correctly. |

### Net effect (Round 2)

The call-setup delay attributable to polling is gone in the common case (WebSocket connected), with a proven fallback for when it isn't. Calls between users on restrictive/carrier NATs now have a TURN relay available where none existed before, authenticated with short-lived credentials rather than a scrapable static secret. Every fix in both rounds is now deployed and live.
